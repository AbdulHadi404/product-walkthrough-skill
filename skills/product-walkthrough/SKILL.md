# Product walkthrough

The job is to explain a working product to people who will never read the code: stakeholders of every age, customers, new team members. The output is one guide per audience, built from **real screenshots of the running product**, written so plainly that a first-time reader can follow it, and generated by scripts that live in the repo so the guides stay truthful as the UI changes.

Three commitments shape everything below:

1. **Truth over polish.** Every picture is the real app in a real state. Seed believable data through the product's own API, not mockups or hand-drawn frames. If a state cannot be reached in the capture environment (a live phone call on a laptop), stage the *component* honestly and say so in the hand-off.
2. **One screen, one page, one idea.** Mixed audiences skim. Each page shows one screen, a numbered legend for what the numbers point to, at most six steps, and a short "good to know" box. Terms are defined once, in a glossary at the back.
3. **Safe to send onward.** Customer guides never name internal systems or third-party providers, never show a real password or token (one-time credentials are masked before capture), and never contain the words the team uses internally. Each audience gets its own guide; the admin guide may say things the customer guide must not.

## Workflow

Work through the phases in order. Each has a reference file with the detail — read it when you reach that phase.

| Phase | Output | Read |
| --- | --- | --- |
| 1. Scope | Screen inventory per audience, example persona, list of states worth showing | this file, below |
| 2. Environment | The product running locally in a safe mode, fixture logins, background jobs verified against the database | `references/environment-and-seeding.md` |
| 3. Seed | A believable example company built through the API; cleanup + "make it live" scripts | `references/environment-and-seeding.md` |
| 4. Capture | `scenes.mjs` on top of `scripts/capture-kit.mjs`; screenshots + callout manifest; contact sheet reviewed. Phone screens via adb (`templates/app-scenes.example.mjs`) and any other picture via `scripts/import-shots.mjs` | `references/capture.md` |
| 5. Write | One content module per guide (`templates/content.example.mjs`) | `references/writing.md` |
| 6. Build & review | PDFs via `scripts/build.mjs`, page contact sheets inspected, leaks grepped | `references/layout-and-review.md` |
| 7. Deliver | PDFs sent to the user and committed with the generator + README | this file, below |

Two gates: **before writing**, every planned screen exists as a reviewed screenshot — writing against imagined screens produces legends that point at nothing. **Before delivering**, the customer guide passes a text grep for internal and third-party names, every callout number has a legend line, and the page previews show no page that is only a spilled tips box.

### Phase 1 — Scope

Read the navigation component and the route tree before anything else: the sidebar/menu is the table of contents the product already agreed on, and route guards tell you which audiences exist. Then decide:

- **Shape.** A *product* guide is one section per screen, in menu order. A *setup* guide (admin panel → cloud console → build service → the result on a device) is one part per tool in the order the team performs them, may have a part without pictures when a tool cannot be captured, and ends with a checklist of the manual steps and the example's values (`references/writing.md`).
- **Audiences → guides.** One guide per role that sees a different menu: typically *customers/companies* (client-safe), *platform admins* (may name providers and internals the admin manages), and a short *what a member sees* section inside the customer guide rather than a third guide.
- **Screens and states.** For each menu item list the default screen plus the states a reader needs: a form open and filled with sensible values, a modal, a credentials banner, an empty state only when it is what a new user will meet, the list with real rows, dark mode once. A screen that changes what a user can do (permissions, a switch that stops all activity) gets its own page.
- **The example persona.** A made-up company with a plausible name, sector and staff (avoid real customers' data). Everything seeded uses this persona so every screenshot tells one coherent story.
- **The journey.** Four to six steps that describe the product's core loop in plain words; it becomes the guide's first page and the order of its parts.

Write this scope down before touching the environment; it is the checklist the later gates use.

### Phase 2 — Environment

Run the product locally in whatever mode makes side effects safe (mock integrations, simulated calls or payments, a local database). Two things matter more than they seem:

- **Verify the data path, not only the pages.** Background jobs that populate history, reports and notifications can fail silently (a missing local migration produced a green UI with an empty history for a whole capture run). Query the database after seeding: rows in every table a screen reads from.
- **Fixture logins are test data.** Create or reset them with the product's own seed scripts and keep them in a gitignored env file. Never type the user's real credentials.

### Phase 3 — Seed

Build the persona through the product's API (login → bearer token → the same endpoints the UI calls). It exercises product code, produces consistent derived data (leads from calls, notifications from events) and stays idempotent when written as "find by name, else create". Add two small scripts you will run before every capture: **pre-run** (undo the side effects the capture itself creates: invited users, imported rows, created companies) and **prep-run** (make live states exist right now: start a job, place activity, so "live" screens are not empty). Details and pitfalls: `references/environment-and-seeding.md`.

### Phase 4 — Capture

Copy `scripts/capture-kit.mjs` and write `scenes.mjs` (start from `templates/scenes.example.mjs`): one browser context per audience, `login`, then `goto → interact → shot(name, { callouts })` per screen. Callouts are selectors (`btn:Label`, `a:Label`, `text:Fragment`, CSS); the kit records each element's box into `manifest.json` so the builder can draw numbered badges in the right places. Mask one-time secrets before the shot. Order scenes so a screen's side effects do not pollute a later screen (capture the CRM before placing the ad-hoc call that creates a nameless lead). Then make a contact sheet of the screenshots and look at every one before writing. Selector, waiting and staging rules: `references/capture.md`.

### Phase 5 — Write

One content module per guide. Structure: cover → "what it does in one minute" + the journey → contents → parts (one per menu area) → one section per screen → appendix (glossary, quick answers, status tables). Every section: a two-sentence summary, the screenshot with its legend, "How to do it" steps, "Good to know" tips, optional tables of statuses. The audience rules (sentence length, defined terms, chips for button names, what never to say) are in `references/writing.md` — read it before writing the first section; rewriting fifty sections later is the expensive path.

**Theme.** The guide wears the product's colours, not the template's. Read the app's design tokens (the primary/accent colour, a soft tint of it, the ink; a brand orange, a brand green, whatever it is) and set `theme` in the content module — `accent` and `accentSoft` at the least. The badges, eyebrows, part dividers, pills and journey tiles all take it. Leave the "Good to know" green unless the brand has its own success colour. A guide left in the template's indigo reads as another company's document.

### Phase 6 — Build and review

`python3 shrink.py` (1.5× JPEGs keep the PDF light), `node build.mjs content.mjs OUT-NAME`, then render every page at 50 dpi with `pdftoppm` and tile them into contact sheets (`scripts/contact-sheet.py`). Look for: a page holding only a "Good to know" box, a table split across pages, a legend whose numbers skip, the table of contents overflowing into the first part divider, a tall form screenshot squeezed unreadably. Fix the CSS or the content, rebuild, look again. Finish with `pdftotext … | grep -i` for the forbidden-word list of each guide. Layout decisions and the defect catalogue: `references/layout-and-review.md`.

### Phase 7 — Deliver

Send the PDFs to the user directly (file delivery tool) and commit them at the repo root with the generator under `scripts/walkthrough/` and a README that says how to rerun the loop (environment → seed → pre-run → prep-run → scenes → shrink → build → review). In the hand-off say plainly: which states were staged and why, which screens are placeholders in the product ("coming soon"), page counts and file sizes, and where the generator lives.

## Quality bar

A stakeholder who has never seen the product should be able to open the customer guide at any page and understand what that screen is for in ten seconds, then do the task by following the numbered steps. A client should be able to receive it without the team worrying about a leaked name, key or internal term. A developer should be able to regenerate it after a UI change in under half an hour by following the README.

## Hard-won gotchas

- `innerText` reflects CSS `text-transform`: a tab labelled "Simple form" in a `capitalize` class reads "Simple Form", an uppercase heading reads "OVERDUE". Wait on text case-insensitively; select by `textContent`.
- A page's first compile in a dev server can exceed a minute; wait up to 90 s, then reload once before giving up.
- Simulated backends fail some actions on purpose (a mock carrier refusing 15 % of dials); wrap those clicks in a retry.
- "Running" is not "live": a job with only pending retries shows nothing in a live view. Start a fresh one just before capturing live screens.
- Write the manifest after every screenshot, not at the end; a crash at screen 40 must not lose 39 callout maps. The kit also read-merges it, so several kits (a laptop, a phone, a tablet) can share one shots directory without the last one to close overwriting the others.
- A viewport shot of something below the fold: pass `focus: "<selector>"` to `shot`; the kit scrolls it to the middle first and records viewport coordinates. Full-page shots are always taken from the top.
- Badges sit just left of the element they mark, level with its first line, so they never cover the words; tall figures are capped at 160 mm so a section's heading, figure and legend share a page — a heading alone with its picture overleaf was the commonest layout defect.
- Feature switches that ship "off" in a fresh database (a platform-wide dialing switch) silently empty half the guide; check them in Phase 2.
- Dev overlays (Next.js's `nextjs-portal`) render into screenshots; hide them with an injected style before every shot.
- The same screenshot serves both guides only when both audiences see exactly the same thing; an admin acting inside a customer workspace has an extra switcher in the top bar, so capture it separately.
- A full-page shot of a form beside a sidebar is squeezed to 4 pt labels in the PDF; capture the form's container with `clip:` instead.
- Pagination follows the font that actually loaded (Google Fonts online vs. a narrower fallback offline). Review the sheets of the build you deliver.
- Emulator captures: wait for a content label via `uiautomator dump`, never a fixed sleep — a swipe on a skeleton screen opens whatever is under the finger; portaled sheets are absent from the dump, tap them by coordinate; match labels loosely (Arabic ى/ي).
- Third-party dashboards block injected scripts (CSP) and cannot be captured from inside the page; use a screenshot saved to disk, or write the part as steps and say so.
- On Windows: `import()` of a bare `C:\` path fails (`pathToFileURL`), `pdftoppm` is usually missing (PyMuPDF instead), and `sharp` for `import-shots.mjs` ships prebuilt for 0.33+.
